# Backend Structure Document

This document outlines the backend setup for the KinLink Family Tree App. It explains how we store and manage data, how the server components work together, and how everything is hosted and secured. You don’t need a deep technical background to follow along.

## 1. Backend Architecture

Our backend is built on Supabase, a managed service that combines a PostgreSQL database, authentication, real-time communication, and file storage. We add Drizzle ORM on top to handle database migrations and complex transactions in a clean, type-safe way.

Key design patterns and frameworks:

- **Service Layer Pattern**: All business logic lives in dedicated service files (`authService`, `memberService`, etc.). This keeps our code organized and testable.
- **Drizzle ORM**: We use Drizzle to define our database schema and run migrations. It gives us type safety and helps us wrap multi-step operations in transactions.
- **Supabase Client**: The mobile app talks directly to Supabase’s auto-generated RESTful endpoints for most operations. For complex transactions, it calls our service layer through Edge Functions.
- **Real-Time Channels**: Supabase Realtime provides live updates over WebSocket channels scoped to each family tree (e.g., `tree-updates:<tree_id>`).

How this supports scalability, maintainability, and performance:

- **Scalability**: Supabase automatically scales its database and real-time layer. We avoid bottlenecks by letting it handle connection pooling and load balancing.
- **Maintainability**: The service layer, Drizzle migrations, and strict TypeScript types ensure changes are localized and easy to reason about.
- **Performance**: Supabase caches query plans, and our use of TanStack Query on the client side minimizes unnecessary requests and keeps data fresh.

## 2. Database Management

We rely on PostgreSQL (via Supabase) for all our structured data. Here’s how we manage it:

- **Database Type**: Relational (SQL) database, using Supabase’s managed PostgreSQL service.
- **ORM**: Drizzle ORM defines tables, columns, and relationships in code. It also runs migrations and supports transactions.
- **Schema Management**: All schema changes go through versioned Drizzle migrations, tracked in our code repository.
- **Data Access**:
  - **Direct CRUD**: Most simple operations use Supabase’s auto-generated REST API.
  - **Transactional Operations**: Complex, multi-step processes (like adding a member, creating relationships, uploading photos, and logging activity) are wrapped in a Drizzle transaction to ensure data integrity.
- **Real-Time**: Supabase Realtime provides push-based updates. Clients subscribe to channels for live collaboration.
- **File Storage**: Supabase Storage buckets hold user-uploaded photos.

## 3. Database Schema

Below is a human-friendly description of our main tables, followed by the PostgreSQL schema.

Tables and their purpose:

- **users**: Stores authentication data and basic profile information.
- **trees**: Represents a family tree. Each tree belongs to a user or group of users.
- **members**: Holds individual family members, with fields like name, birth date, photo URL.
- **relationships**: Links two members together and describes their relationship type (parent/child, spouse, etc.).
- **activity_log**: Records events such as member additions, edits, and photo uploads.

PostgreSQL Schema:

```sql
-- users
CREATE TABLE users (
  id uuid PRIMARY KEY,
  email text UNIQUE NOT NULL,
  full_name text NOT NULL,
  created_at timestamp with time zone DEFAULT now()
);

-- trees
CREATE TABLE trees (
  id uuid PRIMARY KEY,
  name text NOT NULL,
  owner_id uuid REFERENCES users(id) ON DELETE CASCADE,
  created_at timestamp with time zone DEFAULT now()
);

-- members
CREATE TABLE members (
  id uuid PRIMARY KEY,
  tree_id uuid REFERENCES trees(id) ON DELETE CASCADE,
  first_name text NOT NULL,
  last_name text NOT NULL,
  birth_date date,
  photo_url text,
  created_at timestamp with time zone DEFAULT now()
);

-- relationships
CREATE TABLE relationships (
  id uuid PRIMARY KEY,
  tree_id uuid REFERENCES trees(id) ON DELETE CASCADE,
  member_a uuid REFERENCES members(id) ON DELETE CASCADE,
  member_b uuid REFERENCES members(id) ON DELETE CASCADE,
  relation_type text NOT NULL,
  created_at timestamp with time zone DEFAULT now(),
  UNIQUE (member_a, member_b, relation_type)
);

-- activity_log
CREATE TABLE activity_log (
  id uuid PRIMARY KEY,
  tree_id uuid REFERENCES trees(id) ON DELETE CASCADE,
  user_id uuid REFERENCES users(id),
  action text NOT NULL,
  metadata jsonb,
  created_at timestamp with time zone DEFAULT now()
);
```

## 4. API Design and Endpoints

We rely primarily on Supabase’s auto-generated REST interface, supplemented by a few custom Edge Functions for complex flows.

RESTful endpoints (auto-generated by Supabase):

- `POST /auth/v1/signup` & `POST /auth/v1/token` – User registration and login.
- `GET /rest/v1/trees` – List all trees user has access to.
- `POST /rest/v1/trees` – Create a new tree.
- `GET /rest/v1/members?tree_id=eq.<tree_id>` – List members in a tree.
- `POST /rest/v1/members` – Add a new member.
- `PATCH /rest/v1/members?id=eq.<member_id>` – Update member details.
- `GET /rest/v1/relationships?tree_id=eq.<tree_id>` – List relationships.
- `POST /rest/v1/relationships` – Create a new relationship.
- `GET /rest/v1/activity_log?tree_id=eq.<tree_id>` – Fetch recent actions.
- `POST /storage/v1/bucket/photos/upload` – Upload a member’s photo.

Custom Edge Functions (optional) – handle full “Add Member” transaction:

- `POST /functions/v1/add-member` – Takes form data, runs a Drizzle transaction to insert member, link relationships, upload photo, log the action, and returns the new member record.

These endpoints let the frontend and other clients talk to the database securely and reliably.

## 6. Infrastructure Components

- **Load Balancer & API Gateway**: Supabase routes HTTP and WebSocket traffic through a managed gateway.
- **CDN**: Supabase Storage is fronted by a CDN for fast photo delivery worldwide.
- **Caching**: Database query plans are cached, and Supabase uses Redis to accelerate auth tokens and real-time channels.
- **Edge Functions**: Serverless environment close to the user for low latency on custom API calls.

All components work together to ensure fast responses, global availability, and a smooth user experience.

## 7. Security Measures

- **Authentication**: Supabase Auth issues JWT tokens. Every request is checked against the token.
- **Row Level Security (RLS)**: We enable RLS policies on all tables so users can only see data they own or have been granted access to.
- **Authorization**: Custom policies ensure only the tree owner or invited collaborators can read or modify a tree.
- **Encryption**: Data is encrypted in transit (TLS) and at rest in Supabase’s managed disks.
- **Least Privilege**: Edge Functions run with a service role key, but client requests use an anonymous/public key with limited permissions.
- **Input Validation**: All incoming data is validated with Zod on the serverless functions and re-checked by database constraints.

## 8. Monitoring and Maintenance

- **Supabase Dashboard**: Live query metrics, logs, and usage charts.
- **Error Tracking**: Integrate Sentry (or similar) in Edge Functions to capture runtime errors.
- **Performance Alerts**: Set up alerts on slow queries, error rates, and capacity thresholds.
- **Database Backups**: Supabase automatically takes daily snapshots. We also run on-demand backups before major migrations.
- **Drizzle Migrations**: Versioned in Git; applied via CI/CD when merging to main.
- **Dependency Updates**: Regularly update Supabase client, Drizzle, and TypeScript to stay on supported versions.

## 9. Conclusion and Overall Backend Summary

Our backend is centered on Supabase’s managed PostgreSQL service, enhanced by Drizzle ORM for schema and transaction control. We use a clear service layer to keep business logic organized, and we rely on auto-generated REST endpoints plus a few custom Edge Functions for complex flows. Real-time updates, a global CDN, and built-in authentication make the system fast, reliable, and secure.

This setup meets KinLink’s goals by:

- **Ensuring Data Integrity**: All multi-step operations happen in atomic transactions.
- **Supporting Real-Time Collaboration**: Live updates keep everyone in sync.
- **Promoting Security**: RLS, JWTs, and encryption protect user data.

With this architecture, KinLink has a solid, production-ready backend that balances simplicity, performance, and security.
